ATAMO Tokenomics

This page describes the ATAMO supply model, minting limits, participation utility, fee model, and administrative controls based on the deployed Ethereum Mainnet contracts.

Tokenomics statements should be evaluated together with verified contract source code, signed Git tags, signed checksum manifests, official deployment records, and public on-chain data.

Tokenomics Summary

Supply Model

Hard maximum supply: 200,000,000 ATMS.

Issuance Control

Minting is restricted to timelock-authorized execution within the supply cap.

Contract Fees

No token-level transfer tax in the current token logic.

Administrative Model

2-of-3 Safe authorization with timelock-controlled execution.

1. Supply model

ATAMO operates under a hard maximum supply of 200,000,000 ATMS.

The deployed SecureToken contract enforces this cap during mint execution.

The cap is enforced in base units using the token's 18 decimals: MAX_SUPPLY * 10 ** decimals().

Maximum supply in base units: 200000000000000000000000000.

2. Issuance and minting policy

Minting is restricted to the timelock-controlled execution path.

The mint function is: mintByTimelock(address to, uint256 amountBaseUnits)

Minting can only be called by the Timelock and cannot exceed the hard-coded maximum supply.

Minting is also blocked while the token is paused.

No externally owned wallet can directly mint ATMS through the deployed token logic.

4. Distribution disclosure

Any allocation table, treasury distribution, vesting arrangement, liquidity plan, or public distribution schedule should be treated as official only when it is published through ATAMO's official references and supported by verifiable on-chain data or signed release records.

The current core token contract enforces the maximum supply and timelock-controlled mint authority. It does not by itself enforce a public allocation table, vesting schedule, or liquidity-lock schedule.

Distribution verification rule

  • verify recipient addresses on-chain
  • verify mint transactions through Timelock and token events
  • verify any vesting or lock contracts separately if published
  • verify signed release artifacts before relying on allocation claims
  • do not rely on screenshots, social posts, or unofficial tokenomics summaries

5. Participation utility

ATMS can be used with the ATMSParticipationVault for staking, proposal creation, proposal support, generic signal submission, cooldown-based withdrawals, and penalty-funded reward participation.

The Participation Vault is a separate participation and registry layer. It does not directly execute privileged token governance actions.

Participation mechanics

  • staking creates independent staking lots
  • maximum active lots per wallet is 5
  • participation rights require mature active stake
  • minimum participation stake is 50,000 ATMS
  • reward eligibility age is 30 days
  • proposal support is based on eligible reward-share weight
  • early unstaking may create penalties that fund rewards

The Participation Vault uses staking lots. Each lot has its own start time, remaining amount, and lifecycle.

Reward and support weight are based on eligible mature stake and contract-defined weighting rules.

7. Taxes and fees

The current ATAMO token logic does not include buy-tax, sell-tax, or transfer-tax controls.

Standard ERC-20 transfers do not apply hidden token-level transfer fees in the current deployed token logic.

This should be understood separately from Participation Vault penalties. Early unstake penalties are vault-specific and apply only to vault withdrawal behavior according to contract rules.

8. Burn policy

The current SecureToken contract does not expose a public burn function.

No burn mechanism should be claimed unless a future verified contract upgrade or separate official burn process is published and verified.

9. Administrative control and upgrade constraints

Administrative authority exists and is disclosed. It is constrained through Safe authorization, Timelock scheduling, and contract-level checks.

The protocol is not immutable. Future governance-approved upgrades may change behavior. Users and integrators should monitor governance activity continuously.

Current hard constraints

  • minting must pass the token's maximum supply check
  • minting is restricted to the Timelock
  • pausing and unpausing are restricted to the Timelock
  • SecureToken upgrades require explicit upgrade approval
  • Timelock upgrades must be executed through Timelock self-call authorization
  • administrative actions are intended to be visible before execution through timelock scheduling

11. Anti-manipulation controls

  • no token-level transfer tax in the current token logic
  • no token blacklist function in the current token logic
  • no unrestricted public mint function
  • no direct single-wallet token administration path
  • minting cannot exceed the hard maximum supply through the defined mint path

These controls do not remove all governance or upgrade risk. They define the current deployed contract behavior and the current governance constraints.
